# Piks - Sports Betting Battle Platform

### Overview
Piks is a Next.js sports betting platform enabling competitive 1v1 betting battles. Users can engage in real-time matchups against friends or random opponents, with the winner taking the pot (minus a 5% rake). The platform aims to provide a high-end, engaging, and competitive sports betting experience, featuring Quick Match, Play a Friend, Private Match, battle history, social functions, multi-player Pik Pools, and an education marketplace.

### User Preferences
- No purple gradients — purple signals "vibe coding". Use blue, emerald, cyan, and orange for premium look.
- No hover effects on mobile/iPad — use `@media (hover: none)` to disable hover states on touch devices.
- High-end aesthetic — should look like a billion-dollar company is behind it. Clean, minimal, professional.
- "Cancel Friend Request" not "Withdraw Request" for cancelling sent friend requests.
- Navigation labels: `/dashboard` is labeled **"Battle"** (the place to start a battle, formerly "The Lab"); `/battle` is labeled **"Social"** (a feed/social view of live battles, no longer the entry point for starting a battle). Routes are unchanged — only labels.

### System Architecture

#### UI/UX Decisions
The platform employs a clean, professional, and minimal design with a black background, glass-morphism card effects, and a prominent Piks logo. Mobile navigation uses a hamburger menu with swipe gestures, and the bet slip is a floating button that expands to full-screen on mobile. Sticky elements include the TopNavbar and a "Docking Header" on the dashboard. A unified sports filter uses a single row of pills, with "Live" prominently displayed, and games are sorted chronologically.

The `/battle` page (labeled "Social" in nav) renders an Instagram/Facebook-style feed via `components/social/SocialFeedPage.js`: a horizontally-scrolling "live battles" stories rail at top, a Facebook-style **post composer** ("Share something with the league…" — expandable textarea that publishes to `/api/social/posts`) with a thin Quick/Friend/Private battle-shortcut footer so battle entry isn't lost, a grouped pending pile (battle invites + friend requests), and a vertical mixed feed of user post cards, live-battle post cards, recent result cards, and your-recent-match summary cards interleaved chronologically. User posts (`PostCard`) support like + inline comment threads (lazy-loaded, in-place reply composer). Posts persist in `social_posts` (with `social_post_comments` and `social_post_likes`); APIs at `pages/api/social/posts/{index,[id]/comments,[id]/like}.js` are session-gated via `getServerSession`. Desktop gets a right sidebar with a compact Battle CTA, online friends list, and recent winners. The active matchup is a slim one-line banner (the full hero VS card lives on the dashboard, not here). `tailwind.config.js` enables `future.hoverOnlyWhenSupported: true` so every Tailwind `hover:` utility is automatically gated under `@media (hover: hover)` — touch devices never get hover styles.

#### Technical Implementations
Built on Next.js 14.2.30 with Tailwind CSS, the platform uses React Context for state management and NextAuth.js v4 for authentication (email/password and JWT sessions). Drizzle ORM with `@neondatabase/serverless` handles database interactions. LocalStorage persists beta access, demo platform, and challenge selections.

#### Feature Specifications
Piks offers Challenge Tiers (Starter, Pro, Elite) with specific funding, profit splits, and rules (min picks, risk %, max daily loss/drawdown, profit targets). Global popups are used for challenges, demo, authentication, and session summaries. An Admin Panel provides comprehensive management of users, bets, staff, analytics, and withdrawals, including bulk mock user generation and data cleanup. A robust Withdrawal System supports various payment methods. User tracking and analytics monitor interactions and bet activities. The Education Marketplace allows verified cappers to sell picks and Discord access via subscriptions, with reviews and performance stats.

The 1v1 Battle System, inspired by Trivia Crack, includes Quick Match, Play a Friend, and Private Match. Battle Game Modes are **RUSH** (10,000 coins, 6 props from a chosen live game — both players vote on a live game, host wins ties, then race through 6 auto-generated questions on a server-authoritative 15s-per-question timer; most-correct wins, tiebreak by fastest cumulative answer time; gameplay lives at `/battle/rush/[id]` and rush state is persisted as JSONB on the matchup row), **ORIGINAL** (10,000 coins, full day games, highest balance wins), and **TOURNAMENT** (100,000 coins, 3-day battle).

**Rush in-popup ritual (QuickMatchModal):** When a Rush match is found via QuickMatchModal, the modal stays open and carries the user through the **entire match** (pre-game ritual + question gameplay + result) as additional slides instead of redirecting away. Steps after `'found'` are `'rush-vote'` → `'rush-ready'` → `'rush-countdown'` → `'rush-playing'` → `'rush-completed'`, then auto-exit to `/battle`. The routed `/battle/rush/[id]` page is still mounted as a deep-link / refresh fallback — it detects each phase (`voting` / `ready_check` / `playing` / `completed`) and renders the corresponding overlay (RushVotingOverlay / RushReadyOverlay) or full-page view (RushPlayingPhase / RushCompletedPhase). The vote slide is cartoon-themed (2.5px black borders + 4px hard shadow + bouncy badge animations), shows up to 3 live games (`RUSH_VOTE_GAME_LIMIT`) with big tabular scores, and renders each player's pick as a colored checkmark badge — **blue (`#3b82f6`) for YOU, orange (`#fb923c`) for OPP** — so disagreement is visible at a glance (with a green "Locked!" pill when both pick the same game). When the opponent is a bot (`matchup.isFakeOpponent`), `pages/api/battles/rush/[matchupId]/vote.js` records a synthetic bot vote with the same `gameId` so voting always resolves. **Ready check:** after voting resolves the server flips phase to `ready_check` (not `playing`); both players must POST `/api/battles/rush/[matchupId]/ready` (`pages/api/battles/rush/[matchupId]/ready.js`) and the bot is auto-readied server-side after `BOT_READY_DELAY_MS=3000`. There's also a `READY_AUTO_TIMEOUT_MS=15000` UI hint that paces the ready slide. **Stale-ready auto-cancel:** if `ready_check` sits unresolved for `READY_STALE_CANCEL_MS=30000` (only possible in human-vs-human when one side ghosts — bots auto-ready well before this), the next `/api/battles/rush/[matchupId]/state` poll calls `shouldCancelStaleReady` + `cancelStaleMatchup` (`lib/rush.js`), flips `rush.phase` to `'cancelled'` with a `cancelledAt` timestamp, sets `matchups.status='cancelled'` (no winner, no payout, no penalty), and fans out a `matchup:rush:update` SSE event. The routed `/battle/rush/[id]` page renders `RushCancelledOverlay` (cartoon-themed "🕒 Match cancelled — your stake is safe" with auto-exit to `/battle` after 4s), and `QuickMatchModal` closes the in-popup ritual and routes to `/battle?rushCancelled=1` so the user is never trapped on the ready screen. The ready slide shows a green pulsing "I'm Ready" button + per-player ready badges; once both are ready the server flips to `playing` and the modal advances into the 3-2-1 countdown. **In-popup gameplay** (`RushPlayingSlide`) ports the same progress-dot / timer-bar / question-prompt / answer-options layout as the routed `RushPlayingPhase`, with live "YOU / OPP" score chips at the top; the bot auto-answers each question after a deterministic 4-12s delay (seeded by question id) inside `applyBotAutomation` in `state.js`. **Result** (`RushCompletedSlide`) shows winner headline + per-player score grid and auto-exits to `/battle` after `RUSH_RESULT_AUTO_EXIT_MS=12000`. The modal polls `/api/battles/rush/[matchupId]/state` every 750ms plus subscribes to the SSE channel via `getBattleStreamClient` for all five rush sub-steps. Closing the modal mid-rush hands off to `/battle/rush/[id]` so the user is never orphaned in an active matchup. Other modes (original/tournament) still show the original "Continue to Battle" button. Other navigation entry points (LiveBattlesSection inline match-found, IncomingInviteModal, NotificationsDropdown) still use `navigateToBattleStart` directly and rely on the fallback overlays on the rush page.

**Rush questions are sport-aware player props.** `lib/rush.js` exports a `STAR_PLAYERS` map keyed by sport (`nba`, `nfl`, `mlb`, `nhl`) that maps team identifiers to a roster of star players. `generateQuestions(matchup, game)` builds 6 prediction-style questions ("Will <Player> score over X points / hit a home run / etc.?") drawn from both teams' rosters. Each question carries a sealed `correctKey` chosen at generation time so grading is deterministic and the bot's "correctness rate" (currently random with even payout odds) can be tuned later without touching client code.

Users can forfeit battles. A Live Battles Showcase displays active battles to spectators with real-time chat. Gamified elements include fighting-game-style animations for MatchLobby, MatchResult, and QuickMatchModal, and a gamified VS hero card showing real-time player data. Users can withdraw sent friend requests. Customizable User Profiles support usernames, avatars, bios, and battle stats, with avatar uploads leveraging Replit Object Storage. The Pik Pool System facilitates multi-player betting competitions.

#### System Design Choices
The authentication flow covers beta access, NextAuth.js, JWT sessions, user profiling, and challenge selection. A comprehensive Database Schema supports core functionalities. A Bet Autograding System automatically grades pending bets and updates bankrolls. The API architecture is RESTful. A context-specific balance system ensures accurate user balances tied to active challenges (1v1 or Pik Pool), enforcing mutual exclusivity. Promo slot tracking and item share tracking are implemented for analytics, respecting user opt-out preferences. Server-side checks enforce analytics opt-out. The top-nav click-trap watchdog (`utils/topNavClickTrapWatchdog.js`, installed via `GlobalClickTrapWatchdog` in `pages/_app.js`) is **scoped to `/messenger` and `/notifications` only** — an earlier revision installed it on every route, but its heuristic ("auto-remove any fixed-position element ≥90% × 90% of the viewport that isn't tagged `data-allow-fixed-overlay='true'` every 1.5s") was destroying legit UI: the mobile bet slip when expanded to fullscreen, walkthrough popups, and any modal whose author hadn't added the opt-out attribute would flash on for ~half a second and vanish. The condensed sticky sports-pills header (`TopNavbar.js`, gated by `showCondensedBar`) is `hidden sm:block` — on phone widths it overlapped the balance pills + bell + chat + Pik Slip cluster, leaving the horizontally-scrolling pills clipped.

#### Security Architecture
- **Admin auth**: Signed JWTs (HS256) issued by `lib/adminAuth.js`, signing key from `ADMIN_JWT_SECRET` (falls back to `NEXTAUTH_SECRET`). 7-day TTL, issuer `piks-admin`. Tokens carry id/email/type (`admin` | `staff`)/role/permissions. Every request is re-validated against `admin_users`/`admin_staff` to honor deactivation.
- **Endpoint coverage**: Every `/api/admin-panel/*` route is wrapped with `requireAdmin(handler)`. `staff.js` and other multi-permission endpoints additionally check `req.admin.permissions`.
- **Bootstrap admin**: `pages/api/admin-panel/seed.js` returns 410 in production, requires `ADMIN_SETUP_SECRET` env var (no default), and accepts the password from the request body (min 12 chars). Existing seeded admin can be migrated via `node scripts/rotate-admin-password.js` (`ADMIN_EMAIL`, `ADMIN_NEW_PASSWORD` env vars; `ADMIN_TABLE` toggles `admin_users` vs `admin_staff`).
- **Atomic money flow**: Bet placement (`pages/api/bets/place.js`) and withdrawal creation (`pages/api/withdrawals/index.ts`) deduct balance via a conditional `UPDATE … SET col = col - $stake WHERE … AND col >= $stake RETURNING col`. Concurrent requests cannot both pass when only one stake fits. Bet inserts run after the deduction; on insert failure, the deduction is reversed via a compensating UPDATE.
- **Secrets hygiene**: `.env.local` is ignored. After deploy, anyone who had checked-in `.env.local` should run `git rm --cached .env.local` once.

### External Dependencies
- **Authentication**: NextAuth.js v4
- **Database**: Replit PostgreSQL (Neon-backed) via Drizzle ORM
- **Payment Processing**: Stripe
- **Sports Data**: Goalserve API (primary source)
    - **Goalserve REST API**: Main data source for games and odds with caching.
    - **Goalserve WebSocket**: Real-time scores and in-play odds.
    - **Goalserve Inplay HTTP Feeds**: Alternative real-time data.
    - **Supported Sports**: NBA, NFL, NCAAB, NCAAF, MLB, NHL, Soccer, Euro Basketball, Int'l Hockey.
    - **Zero-Delay SSR Architecture**: Instant rendering of live and scheduled games via SSR and continuous cache warming.
    - **Real-Time Possession Polling**: Dedicated service polls and broadcasts possession changes via SSE.
- **Simulated Games Fallback**: `lib/simulated-games.js` generates demo games when Goalserve data is unavailable.
